# U2-DW 百分比判断方法与证据

> 公开副本说明：本文中的“本机”指原开发环境。公开仓库不含官方更新器、提取固件、抓包及原始操作日志；标注“仅本地保留”的证据不随仓库发布。校准与快照为脱敏历史样例，详见 [公开范围](../docs/PUBLICATION.md)。

[项目入口](../README.md) · [验证与已知问题](../docs/VALIDATION.md)

## 当前能做什么

已找到鼠标固件自身的电量分档判断，并能从基站电压缓存反推相应档位。可在这些分档锚点之间做分段插值，得到明确标注为“估算”的连续百分比。尚未找到设备返回的 0–100 容量字段。

**已取得本机满电参考值 414（约 4.14V），连续估算已能实机运行。尚未经过完整放电过程的准确度验证。** 本文不把分档或模拟结果当作准确容量测量。脚本没有校准文件时仍只输出分档；载入已保存的满电参考后，输出明确标为“约”的百分比。

适用范围：`04A5:800A`、接收器版本 `8511`、鼠标版本 `2526`。

## 百分比语义的来源

BenQ《Wireless Mouse DW Version User Manual》V1.03，兼容型号页包含 U2-DW，第 19 页列出电量灯档位：≤25%、26–50%、51–99%、100%，使用中的低电量提示为 ≤10%。

- [BenQ 原版说明书的 PDF 镜像](https://device.report/m/e85b38dd2edabbfe0ca599571908536e93267dab1120e93bf5d2f734f64c4761.pdf)（作者为 BenQ，版本 V1.03，2024-10-28）。
- [ZOWIE 官方 U2-DW FAQ](https://zowie.benq.com/en-ca/support/products/mouse/u2-dw/faq.html)说明开机或充电时会显示电量灯。

新版 DW-D 手册也列出相同档位，但型号不同，本分析以明确包含 U2-DW 的 V1.03 为依据。

## 从固件追踪到的完整路径

分析文件：`firmware-analysis/Mouse_Tx_U2DW.bin`。

SHA-256：`add7a3581e6bff2e7630d60e806fc317fc846e5475e8b974e6faa878bbf20f98`。

1. `0x0CD4` 是电量灯服务入口；`0x0D1A` 读取 `0x20000008 + 0x32` 的有符号采样值作为第一个参数，`0x0D22` 跳转到 `0x247C`。
2. `0x247C` 根据采样值、充电相关输入及开机显示状态选择电量灯处理函数。阈值是 ADC 计数，**不能直接当成毫伏**。
3. 同一个 `0x20000008 + 0x32` 状态量在 `0x0EDE` 被读取，`0x0EEC` 调用 `0x175C`，换算后写入电压结构 `0x200000A8 + 0x20`。
4. `0x175C` 的换算为 `millivolts = floor(adc × 0x3CA50 / 0x38000)`；电压单位为结合数值及电池行为推断。
5. `0x2908` 将该值除以 10、限制到 300–500，再减 300 编码发送。部分状态下，368、369 被修正为 370。
6. 接收器将无线值加 300，保存在缓存中；已验证的 `08 B4 15` 查询返回这个缓存。电脑读到的只有约 0.01V 分辨率，且没有采样时间戳。

因此，电量灯分档与已取得的电压缓存有同源的数据路径，但它们可能在不同时间被刷新。

## 分档阈值

| ADC 范围 | 换算后的内部电压 | 固件路径 | 与说明书对应的电量档位 |
|---|---|---|---|
| ≤3398 | ≤3679mV | `0x237C` 低电量闪烁 | ≤10% |
| 3399–3446 | 3680–3731mV | `0x225C` 开机一格 | 约 11–25% |
| 3447–3510 | 3732–3801mV | `0x22EC` 开机两格 | 约 26–50% |
| ≥3511 | ≥3802mV | `0x2140` 开机三格 | 超过 50%，满电须另判 |

充电路径分别进入 `0x20B4`、`0x20F0`、`0x1FB0`，其显示为第一格呼吸、一格常亮加第二格呼吸、两格常亮加第三格呼吸；使用 3446/3510 两个相同边界。

灯的输出由 GPIO 13、14、15 控制。处理函数最终经 `0x5AB8 → 0xB976` 设置/清除对应 GPIO。`0x2444` 的全关闭模式把三路设高；相对地，`0x1F18` 的满电模式把三路设低。

### 为什么基站读数在边界上不能精确分档

基站将电压截断到 0.01V，因此一个读数可对应多个 ADC 值：

- `373` 对应 ADC 3445–3453，跨越 25% 档位边界。
- `380` 对应 ADC 3509–3518，跨越 50% 档位边界。
- `370` 还可能包含 368、369 的固件修正结果，不能简单逆算成单个 ADC 值。

`battery_percentage.py` 枚举所有兼容的 ADC 值并合并档位，保留这些不确定性。

## 满电不是固定电压比较

在充电路径中，要首次进入 `0x1F18` 的满电显示，至少需要：

- ADC > `0xEC9`，即 ≥3786，换算约 ≥4100mV；
- 第三个状态参数为 0；
- GPIO 9 读取为 1；
- 满足条件的内部计数达到 4000。

已进入满电显示后另有保持逻辑。因此不能把 `raw >= 410` 自动当成 100%，也不能把 4000 次调用直接当作 4000 毫秒。

接收器电压回复的状态字节硬编码为 0，目前没有证据表明上述满电 GPIO/状态能通过现有基站查询读到。

### 对无线包的进一步排查

鼠标 `0x52DA–0x532C` 构造的 9 字节电压无线包中，偏移 1 是 `0x2908` 的电压返回值，后面的字节由已有的校验/按键/滚轮/移动数据复制而来；该组包路径没有读取满电 GPIO 9 或电量灯模式值。

包头高 3 位表示类型 `0x20`，低 5 位在 `0x5264–0x5272` 取自 `0x20000152 + 4` 的通信计数低位。`0x17F8` 会递增/递减该计数，`0x4688` 在通信处理后清零，`0x88B8` 用它判断通信状态；它不是 0–31 级电量或满电标志。

接收器 `0x1232–0x123A` 只把电压字节加 300 写入电压缓存。此排查仅覆盖已确认的电压包与基站查询路径，不声称已排除所有未识别的协议。

由此，当前无法通过这条接口自动确认充满。满电参考采用用户明确确认的三格常亮及随后取下充电后的读数；不能把高电压或长时间读数不变替代这些证据。后文的“约 100%”表示估算曲线顶端，不是新的充满状态确认。

## 连续百分比估算方案

当前实现采用以下分段锚点：

| 电压锚点 | 估算百分比 | 依据 |
|---|---:|---|
| 约 3.40V | 0 | `0x3242` 附近的低电压关停路径，仅作工作范围下限近似 |
| 约 3.679V | 10 | 固件低电量提示阈值与说明书 |
| 约 3.731V | 25 | 固件一格/两格阈值与说明书 |
| 约 3.801V | 50 | 固件两格/三格阈值与说明书 |
| 本机满电、取下充电后的约 4.14V | 100 | 用户确认三格常亮并取下后，末段 15 次读数均为 414 |

在相邻锚点之间线性插值，输出按 5 个百分点取整，限制到 0–100%，始终附加“约”字。即使显示“约 100%”，`full_charge_confirmed` 仍为 false，因为基站查询未提供当前充满信号。这是我们提出的显示算法，不是从固件提取出的连续容量算法。数字步长不代表误差范围。

满电锚点主要用于校准高电量段，不能代替完整放电验证。后续应在固定回报率、相近使用条件下记录自然放电，检查曲线、缓存变化及低电量提示，必要时调整模型。充电、休眠、负载变化都可能影响读数，无法保证每 1% 的准确度。

## 已完成的核对

`analyze_battery_thresholds.py` 用 Unicorn 直接运行提取固件的函数，未向鼠标发送命令：

- 开机显示、普通使用、充电三种输入各扫描 ADC 0–4095，输出分支切换与上表一致。
- 扫描 4096 个 ADC 值验证 `0x175C` 和 `0x2908`，换算模型与执行原始代码的结果没有差异。
- 检查满电条件的边界、GPIO、状态门限、计数及保持逻辑；仅电压高不会进入满电分支。
- 模拟结果保存在 `battery-threshold-emulation.json`。硬件状态函数用明确的输入替代；它验证的是控制流与算术，不是电池容量准确度。
- `percentage-model-arithmetic-check.json` 将 Python 换算与模拟器生成的 142 个编码区间对照，没有差异。
- 历史用户观察“两格常亮、第三格闪烁”，当时原始值 386，高于分档边界，与充电高电量分支相符。精确动作时刻未记录，属于旁证。
- 满电确认前的一次实机查询电压为 414，查询前后版本都为 2526；记录在 `percentage-investigation-snapshot.json`。该快照单独不能证明当时已满电。

上述快照属于此前尚未确认灯态的记录。随后已经完成以下满电校准：

- 人工观察确认三格常亮，保存为 `full-led-confirmation.json`；当时查询值 416，随后短时升至 417。
- 记录启动后提示取下鼠标并正常使用 30 秒，人工确认已取下，保存为 `full-off-charger-confirmation.json`。精确取下时刻未知。
- `full-off-charger-series.json` 的 180 秒记录共 90 次成功读取，变化为 416 → 417 → 416 → 415 → 414。
- 只选取用户确认取下之后、整轮最后 30 秒的数据，15 次均为 414；中位数 414 保存为满电参考。
- `full-battery-calibration-evidence.json` 保存选样、人工确认、原始记录 SHA-256；`full-battery-calibration.json` 保存参考值和固件版本，并标记为单次满电的初版校准，容量准确度未经验证。
- `calibrated-live-percentage.json` 保存校准后的实机读取：原始值 414，估算 100%，标签“约 100%”，设备原生百分比仍为 null。查询前后鼠标版本都为 2526。
- `calibrated-percentage-verification.json` 核对输出范围、随电压单调变化、满电参考映射、断连/未知固件/异常值不显示百分比、原始记录哈希以及实机查询成功。这些核对不代表完成了全程放电准确度验证。

例如，套用当前初版曲线，原始值 387（约 3.87V）会显示“约 60%”。这是模型推算，不是对先前时刻真实容量的测量。

## 使用

```powershell
# 对已有实机快照做分档解释，不访问硬件
python diagnostics/battery_percentage.py --snapshot diagnostics/percentage-investigation-snapshot.json

# 使用本机已保存的满电校准，实时读取一次并输出估算百分比
python diagnostics/battery_percentage.py --live --calibration diagnostics/full-battery-calibration.json

# 对历史快照使用同一曲线
python diagnostics/battery_percentage.py --snapshot diagnostics/percentage-investigation-snapshot.json --calibration diagnostics/full-battery-calibration.json

# 离线重做固件核对；Unicorn 仅为分析依赖
# 注意：固定改写 diagnostics/battery-threshold-emulation.json，复跑前保存旧结果
python diagnostics/analyze_battery_thresholds.py
```

命令从项目根目录执行；解释器和 UTF-8 设置见 [项目入口](../README.md)。

`full-battery-calibration.json` **已创建**，对应这只鼠标的 414 参考值。载入时会检查固件版本、人工确认、参考值以及所引用证据文件中的对应字段；不会在每次加载时重新核验原始记录 SHA-256。不能默认将这份校准用于其他鼠标。实时读取仅使用此前已确认的三个只读查询；不要同时运行其他 HID 诊断，避免无命令回显的回复混淆。

2026-10-05 验收补充：加载器显式验证 JSON 对象结构，证据中的人工确认要求严格的布尔 `true`，拒绝字符串或数字代替。固件离线核对及回归结果见 [本轮验收](../docs/ACCEPTANCE-2026-10-05.md)；估算公式和本机参考值保持不变。

无论是否估算，都必须处理版本清零、设备断开和缓存年龄未知；查询时间不等于电池采样时间。
